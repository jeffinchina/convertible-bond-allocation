# 可转债配债自动日报产品规格说明书

版本：1.4.0
更新日期：2026-10-16
产品目录：`work/hybrid_monitor/`

## 1. 产品目标

在每个 A 股交易日早上自动核验可转债“同意注册公告”和“正式发行公告”，通过邮件给出新增事件、异常状态及“已同意注册但尚未正式发行”的存量候选，支持正式发行前的介入时点判断；正式发行文件确认申购日后，在申购日盘前提供两次可执行的新债申购提醒。

## 2. 运行与输出

- 调度：Windows 计划任务 `可转债配债-混合监控` 保留周一至周五 08:30 定时触发，同时在当前 Windows 用户登录时触发一次状态续跑；休市日由脚本二次判断。计划任务统一传入 `-Scheduled`：北京时间 08:30 前的登录触发直接退出；08:30 后若 `lastSuccessfulCutoff` 已覆盖当日 08:30 也直接退出，避免提前或重复发送日报。任务采用单实例策略，登录触发与 08:30 触发重叠时不会并发执行。
- 运行依赖：日常检索、计算和 SMTP 邮件不依赖 ChatGPT 桌面应用运行或保持登录；事件日深度文字分析由计划任务直接调用项目内置 Codex CLI，依赖其本机登录凭据，但不要求 ChatGPT 窗口打开。当前已验证运行时版本为 `codex-cli 0.153.4`。
- 正常无新增：发送 `【可转债配债】昨日无新公告`，保留原公告核验表并追加存量候选表。
- 发现新公告：生成证据包；事件分析邮件后同样追加存量候选表。同一检查批次包含多个事件时，先逐事件执行关键数据预检：完整事件进入分析、发送并在成功后单独标记为已报告；不完整事件与完整事件隔离，保留为下次重试对象，不得阻断同批次已完整事件。
- 关键来源失败：不发送“无新增”结论，改发监控异常邮件。
- 失败保护：单个 HTTP 请求执行 3 次重试；巨潮公告查询另有官方双域名自动切换。Windows 计划任务保留 `StartWhenAvailable`、“失败后每 10 分钟、最多 3 次”和 1 小时执行上限，并新增用户登录触发作为错过 08:30 后的确定性补跑入口；脚本只在全链路成功后推进检查截止时间，登录补跑从该截止点继续，事件键与邮件正文哈希共同抑制重复发送。
- 申购提醒：独立计划任务 `可转债配债-申购提醒` 在正式文件列明的申购日于北京时间 08:50、09:50 各运行一次，复用既有 QQ SMTP 私有配置和同一收件人清单。标题固定为 `【可转债申购】请今天申购新债：<新债简称>`；正文由确定性程序生成，不调用 Codex、不消耗模型用量，也不重复执行 08:30 公告检索。
- 申购提醒补跑：电脑关机、重启或用户未登录而错过时点后，`StartWhenAvailable` 与当前用户登录触发会在申购日 15:00 前补发尚未完成的批次；若登录时提醒任务先于 08:30 主监控空跑，而主监控随后才发现当天正式公告，主监控会在可靠入队后立即执行同一补发检查，消除登录并发竞态。15:00 起及后续日期不补发已经失去时效的提醒。08:50 与 09:50 分别记账，互不覆盖。

### 2.1 调度身份与凭据约束

- 计划任务以当前用户的 `InteractiveToken`、最低权限运行。该登录类型只有在用户已登录 Windows 时才能启动；电脑关机、重启后尚未登录或用户已退出时，08:30 触发不会创建新的交互式会话。
- QQ SMTP 授权码由 Windows DPAPI `CurrentUser` 加密，Codex CLI 登录信息及部分网络/代理设置也属于当前用户上下文。改用其他服务账号会无法解密现有授权码；改用 S4U 等无密码后台令牌又可能缺少网络访问能力，无法可靠完成交易所 HTTP 检索和 SMTP 发送。因此不把任务改成脱离用户会话的服务账号运行。
- 登录触发用于弥补上述约束：用户在 08:30 后登录且当日基准尚未成功处理时，启动同一状态化监控，按 `state.json.lastSuccessfulCutoff` 补齐遗漏窗口；08:30 前或当日已成功时无害退出。登录触发不改变每日 08:30 基准，也不依赖 ChatGPT 桌面应用是否启动。
- 申购提醒任务使用相同的当前用户 `InteractiveToken` 和 DPAPI 邮件凭据，拥有周一至周五 08:50、09:50 及登录三个触发器，采用单实例、`StartWhenAvailable`、失败后每 10 分钟重试且最多 3 次、15 分钟执行上限。它不依赖 ChatGPT 桌面应用；用户会话未建立时不能运行，登录后仅补发当日 15:00 前仍有效的批次。

## 3. 数据来源与状态流转

- 公告：上交所、深交所、巨潮资讯、证监会官网。巨潮查询优先使用 `https://www.cninfo.com.cn/new/hisAnnouncement/query`；主站遇到 403、传输失败或非 JSON 响应时，自动切换至巨潮官方备用域名 `https://list.cninfo.com.cn/cninfo/new/hisAnnouncement/query`。同一运行后续请求优先复用已成功端点，下一次运行仍会重新探测主站。
- 正式发行事件分类：只把正式“发行公告”、不带审核阶段后缀的正式“募集说明书”，以及含股权登记日/原股东优先配售安排的发行文件纳入事件；“上会稿、审核稿、申报稿、注册稿、修订稿、草案、预案”等申报或审核阶段文件一律排除。交易所与巨潮同时出现同一审核稿不会提升为正式事件。
- 募集规模：最新可得募集说明书注册稿或同等级正式申报文件；支持“募集资金总额”“预计募集资金量（含发行费用）”“募集资金不超过”“拟发行可转换债券的金额”等常见表述。正式发行解析会收集全部金额候选并按语义排序，明确的“本次发行总额”“本次发行可转债总额”和最终发行规模优先；带“调减、扣减、原拟、原计划、调整前、变更前、取消、撤回”等调整或历史上下文的金额不得覆盖当前最终发行额，也不得制造伪字段冲突。
- 股本：行情股本快照，必要时回退到官方申报文件披露值。
- 行情：不复权行情用于“上一交易日收盘价”和参考转股价；前复权日线用于跨期涨跌与回撤。
- 行业：东方财富 F10 公司概况 `EM2016` 行业层级的末级细分行业；缺失时依次回退证监会行业字段、行情行业字段、最新主营构成中的行业类别。
- 主营业务：东方财富 F10 最新一期主营构成，优先选收入占比最高的产品类别；无产品类别时回退收入占比最高的业务类别，并排除“其他”。
- 题材概念：仅用于申购提醒，取东方财富 F10 核心题材接口中标记为公司特定、且按官方板块顺序排名靠前的最多 5 项概念；不把地域、指数、融资融券等通用板块当作公司题材。接口失败或无特定概念时显示“暂无可靠概念数据”，不得由公告标题或模型猜测，且不阻断包含核心申购代码的时效提醒。
- 行业和主营业务分别清洗、各截取不超过 10 个字符，同时保留原始值、主营报告期和来源链接供复核；任一缺失时不得伪造。
- 盘中运行时必须剔除当日未收盘 K 线，所有现价及定价参考统一截止上一交易日。
- 正式发行阶段不再假定单个首选 PDF 同时披露全部条款。系统在同一事件内按“发行公告、募集说明书、原股东优先配售公告”等文档类型选择补充官方文件，优先交易所来源，下载后按 SHA-256 去除交易所与巨潮的同内容副本；再逐文档解析最终发行规模、可配售股份基数、实际每股优先配售额、初始转股价、股权登记日和申购日，并按字段合并，保留 `fieldSources` 来源追踪。
- 正式股份基数会收集“截至某日公司总股本”“发行人/公司现有总股本”“公司股本总额”“可参与原股东优先配售的股本总额/数量”等全部候选；明确标注可参与优先配售的基数优先。在已知发行额和每股配售额时，再以 `候选股数 × 每股配售额` 与最终发行额的一致性择优，差异阈值为 0.5%，从而排除回购专户等不可配售股份。无候选通过时判定为不完整，不以公司总股本强行补齐。
- 正式日程只从明确的股权登记日、原股东优先配售认购日或网上申购日标签提取，支持多个申购标签共用同一日期；不得把前文的股权登记日误作申购日。针对 PDF 表格可能按“日期列→事项列”压平的抽取顺序，带 `T-1` 的日期与其后近距离“股权登记日”事项作为高置信度同一行，优先于标签后紧邻的下一行日期，避免把 `T` 日申购日误判成登记日。正式条款合并后再抓取截至运行时点的最新已完成交易日不复权收盘价及 10/20 日行情；盘中运行剔除当日未收盘 K 线。表格按实际行情日期标注，不得误称为“公告日前一交易日”，也不允许把这些可取得数据交给模型猜测或显示为“待补证”。
- 正式发行文件额外确定性提取新债简称/代码、申购简称/代码、原股东配售简称/代码、债项评级和期限。形成证据包后先写入申购提醒队列，再调用事件日 Codex；因此深度分析或事件邮件失败不会丢失已经确认的未来提醒。历史证据回填会重新解析已有 PDF，用于覆盖升级前已经报告、但申购日尚未到来的正式发行事件。
- 入池：识别到“同意注册”事件。
- 出池：识别到“正式发行”事件；注册批复估算有效期超过 365 天时不再作为可执行候选。
- 每 7 天的历史全量回填以交易所原始公告为必需层：联合检索上交所和深交所，再以巨潮补充注册记录及公司级正式发行复核。巨潮暂时不可用时允许基于两个交易所结果降级重建并记录警告；任一交易所历史检索失败时不得覆盖原存量池。
- 全量回填重新发现同一证券、同一注册日时，保留此前已核验的募集规模、官方股本、行业主营和指标缓存，避免补充源短暂故障导致数据退化。

## 4. 申购日提醒邮件

- 发送硬门槛：正式事件、正股代码与简称、申购日、新债简称/代码、网上申购代码均已从正式文件确定，且 `calculation.status=complete`、正式条款无字段冲突、配售一致性校验无冲突。任一条件不满足时不生成伪完整提醒，保留缺失或冲突原因供修复；申购简称、评级、期限等非核心字段缺失时显示“未披露”。
- 幂等键：提醒记录按“正股代码＋申购日＋网上申购代码”唯一；每条记录的 08:50、09:50 两个批次分别保存 SMTP 成功时间。正式事件重跑会更新基础信息，但不会清空已发送批次；同一事件键或同一“正股代码＋新债代码”出现修订后的日期/申购代码时，旧变体标记为 `superseded` 并永久停止发送。
- 邮件正文：使用手机友好的单列分组表，突出网上申购代码；新债信息包含简称/代码、申购简称/代码、申购日、发行规模、初始转股价、评级、期限和原股东配售代码；正股信息包含简称/代码、带日期的最近收盘价、正股现价/转股价、行业、主营业务与题材概念，并附正式文件链接和“勿混用申购代码/配售代码”提示。
- 发送语义：两个批次使用相同的规定标题，但正文固定写入各自的“本次提醒批次”，使现有正文哈希去重既能抑制同一批次重试，又不会误拦第二次提醒。SMTP 返回“内容已投递过”的重复确认也视为该批次成功。
- 时效边界：日常 08:50/09:50 提醒运行只读取本地队列，不扫描证据、不解析 PDF，也不依赖实时网络或模型；登录补跑只处理申购日当天、目标时点已经到达且 15:00 前仍未成功的批次，跨日不补发。只有显式执行队列重建时才扫描历史证据并强制重解析官方 PDF，以修正升级前或旧解析器留下的日期/代码；重建时题材源暂不可用，不得用空值覆盖同一事件此前已核验的概念快照。

## 5. 存量候选表字段

字段按以下顺序展示，邮件端允许横向滚动：

| 字段 | 展示 | 计算口径 |
|---|---|---|
| 股票 | 简称、六位代码 | 公告证券简称与代码 |
| 行业｜主营业务 | 只占一列、一个单元格；单元格内第一行显示行业，第二行显示主营业务，两项各不超过 10 个字符 | 公司概况细分行业末级｜最新报告期收入占比最高的产品类别，必要时回退业务类别 |
| 每百元含权 | 金额 2 位小数，括号内百分比 2 位小数 | `募集规模上限 ÷ 最新总股本 ÷ 上一交易日收盘价 × 100` |
| 正股现价/转股价* | 百分比，0 位小数 | `上一交易日收盘价 ÷ 参考转股价下限 × 100` |
| 注册日/已过 | 注册日期、已过交易日、有效期估算剩余天数 | 已过交易日不含公告日 |
| 注册后涨跌 | 带符号百分比、上一交易日收盘价 | 公告日或此前最近交易日的前复权收盘至上一交易日收盘 |
| 短期位置 | 近 10 日涨跌、距注册后最高收盘回撤 | 前复权日线 |
| 配售1手（10张）所需股数 | 整数股 | 理论值 `N0＝1000 ÷ 理论每股配债额`，四舍五入显示到个位数 |

### 5.1 参考转股价说明

正式发行前并没有已确定的初始转股价。日报中的“转股价”是决策参考下限，不是公司公告的实际初始转股价：

1. 前 20 个交易日成交均价＝20 日股票交易总额÷20 日股票交易总量；
2. 前 1 个交易日成交均价＝该日股票交易总额÷该日股票交易总量；
3. 参考转股价下限＝上述两者较高值，并向上取整到 0.01 元；
4. 正式发行后必须改用发行公告披露的实际初始转股价。

成交量按行情源“手”换算为股（1 手＝100 股）。不足 20 个有效交易日成交额或成交量时，本列显示“待补证”，不会用简单收盘均价替代。

### 5.2 配售1手所需股数说明

正式发行前使用募集规模上限和最新总股本估算理论每股配债额。本列与关键数据分析中的理论配 1 手股数 `N0` 保持一致，只在展示时四舍五入到个位数，不按 100 股整手调整。正式发行后应按实际每股优先配售额和交易所配售规则重算。

## 6. 质量控制

- 原始接口响应写入 `raw/`，公告判定写入 `classification_audit.json`。巨潮每页响应附带 `_fetchMeta`，记录首选端点、实际端点、是否切换及此前失败原因；邮件来源状态明确标出官方备用域名已启用。
- 巨潮 PDF 附件继续只允许 HTTPS：标准客户端受 CDN 403/握手限制时，使用 `curl_cffi` 的 Chrome 兼容 HTTPS 通道；下载审计记录 `transport`、`transportFallback` 和主通道错误。两条 HTTPS 通道均失败时保持完整性闸门，不回退明文 HTTP。
- 公司概况、主营构成、行业备用响应和标准化结果分别保存为 `company-survey-raw.json`、`business-analysis-raw.json`、`company-industry-fallback-raw.json`（触发备用时）、`company-profile.json`；事件证据包同时保存 `companyProfile`。
- 文本/JSON 客户端自动识别并解压带响应头或仅带 gzip 魔数的压缩正文；公司概况与主营构成接口对“HTTP 成功但正文为空/非 JSON”的限流响应再执行三次内容级重试。行业另有独立行情字段回退，避免单个页面短暂异常造成整表空值。
- 存量池每日刷新行业和主营业务；当日接口失败时只允许沿用上次成功且完整的缓存，并在警告中标明。无有效缓存时该股票记为补证失败。
- 注册和正式发行阶段均由脚本可信计算 HTML 将“行业｜主营业务”固定为关键数据表第一条数据行，邮件运行器校验后整体注入。该行的数值单元格内以 HTML 换行分隔行业和主营业务，不拆成两行指标。两项任一缺失或超过 10 个字符时阻止生成事件分析邮件。
- 注册和正式发行阶段均必须先由脚本形成 `calculation.status=complete` 的可信计算块，模型只解释结果并输出占位符；邮件运行器统一以脚本 HTML 替换占位符。正式发行阶段关键行情、发行输入或计算任一缺失时直接发送异常通知，不生成低价值邮件。
- 正式事件证据包保存各补充文件的 URL、标题、路径、SHA-256 和逐字段来源。不同官方文件对同一字段给出不同值时写入 `conflicts` 并触发 `formalTermConflict`；发行额、可配售股本和每股配售额的反算差异超过 0.5% 时触发 `allocationConsistency`。上述任一情况均保持 fail-closed，不发送伪完整分析。
- 正式金额冲突判断建立在语义筛选之后：募投项目调减额、历史发行方案金额和调整前金额不作为当前最终发行额参与跨文档冲突；真正的当前最终发行额不一致仍按 `formalTermConflict` 熔断。
- 同批次事件在证据预检后写入 `event-batch.json`：只有 `calculation.status=complete` 的证据路径进入 Codex 分析清单。完整子批次全部发送成功后写入该子批次各事件的去重键；不完整事件不写入去重键，成功截止时间不推进，因而后续运行可继续补证重试。
- 正式发行计算使用公告实际每股优先配售额 `p`；`N0=1000÷p`，保守交易单位股数 `N=100×ceil(N0÷100)`，`M=N×上一交易日收盘价`，`H=1000÷M`，百元含权率=`p÷收盘价`，转股价值=`100×收盘价÷初始转股价`，并计算 15%/20%/30%/40%/50% 五档正股盈亏平衡跌幅。
- 存量状态写入 `pending_inventory.json`，每 7 天全量回填，其余交易日增量更新。
- 存量全量回填必须覆盖上交所、深交所与巨潮，测试应包含“交易所独有注册公告仍入池”“正式发行后剔除”“巨潮失败可降级”“同一注册事件保留已核验补证”四种情形。
- 募集规模、总股本、收盘价等关键字段缺失时保留错误原因，不伪造数值。
- 所有脚本进程、Python 输出和事件分析子进程统一使用 UTF-8；PowerShell 7 强制输出纯文本，Python 在子进程采集、邮件异常构造和 SMTP 异常三个边界清除 ANSI/VT 终端控制码，异常邮件必须保持中文诊断信息可读。
- 无新增结论要求关键官方来源全部成功。
- 邮件按正文哈希去重，SMTP 部分收件人被拒绝时整次发送判为失败。发送账本用跨进程命名互斥锁串行化“查重→SMTP 投递→原子记账”全过程，日报与申购提醒并发时不会互相覆盖去重记录。
- 发件人和收件人仅保存在被 Git 忽略的本机 `work/qqmail-config.json`；标准收件人字段为 `to` 数组，同时兼容旧版单字符串及 `recipients`/`recipient`。公开脚本和示例配置不包含真实邮箱，配置迁移只报告收件人数量并保留 DPAPI 密文。
- 申购提醒状态单独写入被 Git 忽略的 `subscription_reminders.json`，通过进程间文件锁和原子替换避免 08:30 监控与提醒任务并发损坏队列。每个批次只在 SMTP 完整接受或发送脚本确认完全相同内容此前已投递后标记成功；异常不记成功，后续计划任务继续重试。
- 多只新债同日申购时逐只、逐批次发送；一只债券失败不会回滚其他债券已经成功的批次。所有进入标题、HTML 和链接的字段均转义，正文不包含本机证据路径、收件人清单或凭据。

## 7. 维护与验证

- 主程序：`work/hybrid_monitor/monitor.py`
- 配置：`work/hybrid_monitor/config.json`
- 安装/更新计划任务：`work/hybrid_monitor/Install-HybridMonitor.ps1`
- 手动干跑：`work/hybrid_monitor/Run-HybridMonitor.ps1 -DryRun -NoModel`
- 申购提醒入口：`work/hybrid_monitor/Run-SubscriptionReminder.ps1`；干跑可加 `-DryRun`，不会发信或改队列。
- 申购提醒队列回填：`py work/hybrid_monitor/monitor.py --rebuild-subscription-reminders`，强制重解析已有正式发行 PDF 并只重建未来提醒，不发送邮件；普通 `--subscription-reminders` 仅消费现有队列。
- Python 依赖：`work/hybrid_monitor/requirements.txt`（当前固定 `pypdf 5.9.0`、`curl_cffi 0.14.0`）。
- 单元测试：在 `work/hybrid_monitor/` 执行 `py -m unittest -v test_monitor.py test_subscription_reminder.py test_install_hybrid_monitor.py`；计划任务契约测试同时核验 08:30 日报任务与独立 08:50/09:50 申购提醒任务、当前用户登录触发器、`InteractiveToken`、单实例和失败重试设置。
- 验收重点：“行业｜主营业务”位于新增公告关键数据表第一条数据行、存量表股票列之后且只占一个字段；数值单元格内行业在上、主营业务在下；行业和主营各不超过 10 个字符；新列顺序正确；比率保留 0 位小数；1 手股数与理论 `N0` 一致并显示到个位数；无实际转股价时邮件脚注明确“参考估算”；正式发行证据必须包含真实收盘价、实际配售额和初始转股价，关键计算表不得出现“待补证”；多 PDF 条款应逐字段互补并保留来源，冲突和反算不一致必须熔断；同批次完整/不完整事件必须隔离，完整事件可交付且不完整事件保持可重试。莱特光电 `688150` 回归必须选择最终发行额 524,779,000 元，排除历史调减金额 68,000,000 元，识别股本总额 402,437,585 股及可参与优配基数 399,439,136 股，并使发行额、每股配售 1.313 元和优配基数通过 0.5% 一致性闸门。
- 申购提醒验收重点：只有计算完整、无正式条款/配售一致性冲突的正式事件建队列；注册事件和缺少关键申购字段的事件不建队列；08:50、09:50 边界、同日补跑、主监控延迟入队后的即时补发、15:00 截止和跨日不补发正确；两个批次各一次且正文不同；成功、重复确认、SMTP 失败重试、进程重启、重复正式事件、修订事件旧变体作废、同日多债均保持幂等；标题精确，正文包含新债、正股、行业、主营和可靠概念；日常提醒路径不扫描证据、不联网、不调用模型，显式重建必须强制重解析 PDF。

## 8. 边界

本产品提供公告监控、确定性计算与申购操作提醒，不构成投资建议。注册阶段数据均为早期估算，正式发行规模、实际转股价、股权登记日和实际配售比例以正式发行文件为准；申购提醒中的代码和日程仍应在券商页面最终核对。任务依赖本机当前 Windows 用户登录状态，错过申购日 15:00 后不会补发过期提醒。
